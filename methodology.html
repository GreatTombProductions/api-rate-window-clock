How the clock turns a vendor table into a timing answer

The implementation is deliberately small: effective-date selection, weekday-aware UTC band classification, then component-by-component token arithmetic.

1. Select the rate basis by effective time

Every price basis carries an ISO 8601 effective_at timestamp. For a planned start, the calculator selects the latest complete basis whose effective timestamp is not later than the start. A future basis is never applied early. If no basis covers the time, the result is unavailable rather than zero.

The current basis became effective at 2026-08-16 16:00 UTC. That timestamp came from DeepSeek's transition notice captured on August 15. The current pricing pages present the schedule as active but no longer repeat the transition date; the data receipt preserves that provenance distinction.

2. Classify the start time in UTC

The current DeepSeek page says peak hours are 01:00–04:00 and 06:00–10:00 UTC, Monday through Friday. The intervals are half-open:

peak = weekday AND (
  01:00 <= UTC time < 04:00 OR
  06:00 <= UTC time < 10:00
)

That means 03:59 UTC on a Tuesday is peak; 04:00 is off-peak. Saturday at 02:00 UTC is off-peak even though the clock hour would be peak on a weekday. The Chinese page states the equivalent Beijing windows: weekdays 09:00–12:00 and 14:00–18:00.

3. Keep the three token classes separate

Let h be cache-hit input tokens, m fresh/cache-miss input tokens, and o output tokens. Let the band's per-million rates be rₕ, rₘ, and rₒ.

declared cost = (h × rₕ + m × rₘ + o × rₒ) / 1,000,000

The calculator does not replace these with one blended token price. Whether a workload reuses context can materially change which component dominates the estimate.

4. Find the next strictly cheaper boundary

The engine enumerates exact schedule and effective-date boundaries for the next eight days. It recomputes the same token mix at each boundary and returns the earliest one with a strictly lower total. If the workload is already in the cheapest declared band and no announced future basis lowers the amount, it says so plainly.

5. Separate current and announced-future prices

The schema has a dedicated announced_future_bases collection. At the 2026-08-28 build, the live pages published no future replacement table. The site therefore applies only the current basis. A future table would be displayed separately and would remain mathematically inactive until its own effective timestamp.

Source-change gate

The build parses English and Chinese pages independently, normalizes the model IDs, versions, weekday scope, windows, and per-band rates, and hashes those semantic records. A changed semantic hash fails the build until a person or agent reviews the new table and explicitly accepts the pin. Source disagreement sets coverage to conflict and disables estimates; rates are never averaged.

Limits

  • The selected band is based on the batch start time. A job that runs across a boundary may be billed differently request by request; this calculator does not simulate duration.
  • The estimate excludes taxes, reseller markups, retries, credits, undocumented discounts, and provider-side token-count differences.
  • Vision images are converted to input tokens under DeepSeek's separate conversion rule. Enter the resulting tokens; this tool does not infer image token counts.
  • This is a declared-price estimate, not independent proof of what appeared on an invoice. No provider-side per-request billing ledger is used.
  • Times before the current basis's effective timestamp are unavailable. The tool does not reconstruct retired prices.

Reproducibility

The repository includes raw authority captures, source hashes, a dependency-free parser, the normalized semantic pin, Python and JavaScript calculation engines, one shared case table, differential parity tests, and a browser smoke test. See source receipts for the exact build inputs.
